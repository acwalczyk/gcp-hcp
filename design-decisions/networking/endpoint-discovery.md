# Endpoint Discovery from Region + Environment

***Scope***: GCP-HCP

**Date**: 2026-09-23

## Decision

Clients like `gcphcpctl` will resolve service endpoints (OIDC issuer, platform API) from a **public GCP region + environment alone**, by fetching a **per-environment static JSON manifest** served via Cloud CDN over a private GCS bucket from the environment's **service project** (`hcp-openshift-redhat-{env}`). The manifest is **generated in Terraform** from the committed metadata registries (`infra_ids.yaml`, `regions.yaml`) and **re-published automatically** when those registries change. It is a client-agnostic public artifact any client can read. The versioned manifest also advertises a stable per-environment global authorization endpoint for Role and RoleBinding management, using the same Terraform/CDN/GCS mechanism. Its routing follows the manually configured replication leader; discovery does not perform leader election or runtime health aggregation.

## Context

- **Problem Statement**: Operators must hand-configure region-specific hostnames that embed internal-only identifiers (`infra_id`), e.g. `oidc.int-reg-us-c1-nkcw.int.gcp-hcp.devshift.net`. Requiring callers to know and construct these is error-prone, couples the client to internal naming, and does not scale across regions. Users should supply only a public region and an environment.
- **Constraints**:
  - **It sits on the cluster-create critical path.** Discovery is a hard dependency of every cluster-create, so it has to be highly available and can't introduce a fragile runtime — which is what pushes it toward a static, compute-free artifact rather than a service.
  - **The client contract must stay clean.** The request is region + environment alone — users no longer hand-configure or construct `infra_id`-bearing hostnames. Discovery introduces no new internal identifiers; it publishes deployed regional endpoints and the stable global authorization hostname from infrastructure metadata.
  - **Each environment is served in isolation.** dev/integration/stage/production get their own manifest and serving stack, with no shared surface across environments.
- **Assumptions**:
  - `terraform/metadata/infra_ids.yaml` + `regions.yaml` are the source of truth for deployed regions, and advertised endpoint hostnames are a pure function of committed region/environment metadata — so the manifest can be generated by the same GitOps flow that onboards regions.
  - Only **customer-facing (`main` sector)** regions are advertised; a region+environment may host other sectors (e.g. `canary`) that must not appear in the manifest.
  - The env apex zone `{env}.gcp-hcp.devshift.net` is owned by the commons/global project, so the `discovery` record is a cross-project write into that zone.
  - Endpoint data is non-secret and read-only, so it is safe to serve as a public artifact to any client.

## Alternatives Considered

The options were weighed on the same axis — *deterministic-from-committed-metadata → static; live/health-gated → regional*. The chosen option is the static, metadata-derived manifest served from the service project; the three set aside were:

1. **Region-push to a shared GCS object per region**: Each region writes its own endpoint object into a shared bucket. Compute-free like the chosen option and additionally **health-gated** — the object exists only once the region is actually serving — at the cost of per-region cross-project writes and no single-file "list all regions" index.
2. **Global aggregator service (GKE workload)**: A small global workload reads region-published data and serves discovery over HTTP. The most dynamic option, at the cost of a runtime on the client critical path.
3. **Fully global-free, region-served discovery**: No global artifact at all — each region self-publishes an `infra_id`-free DNS name (`discovery.{region}.{env}`) that resolves to a discovery document it serves from its **own** CDN/GCS or platform-api-server. Strongest regional independence and inherently health-gated (the name resolves only while the region serves), at the cost of losing the free cross-region index and relocating region DNS publication out of the global apex zone.

## Decision Rationale

* **Justification**: The endpoint set is a **pure function of committed metadata**, so the correct default is a **static, versioned artifact** produced by the existing region-onboarding GitOps flow — not a service. This delivers the full requirement (region + environment → endpoints) with no compute on the critical path, the strongest HA and Zero-Operator-Access posture, and near-zero new operational surface.
* **Evidence**: A prototype confirmed that endpoint URLs can be derived from committed infrastructure metadata without querying live regional services. The serving stack is not novel either: GCP-621 already runs CDN-over-private-GCS under the same org-policy constraint, so it is a proven, copyable pattern rather than new infrastructure to design.
* **Comparison**: The chosen option is the simplest design that meets the requirement with **no compute on the critical path** — a single artifact generated by a flow that already exists. Every alternative is more complex for capabilities the requirement does not need. The global aggregator (2) is the clearest to reject: it puts a runtime on the client critical path to serve data that is already deterministic. Region-push to GCS (1) and the global-free design (3) do stay compute-free, but each fragments the single deterministic artifact into many independently-published, per-region pieces — more moving parts to operate, coordinate, and reason about — to buy health-gating and regional independence that resolving endpoints from region + environment simply does not require.

## Consequences

### Positive

* Users configure only **region + environment**; internal `infra_id`s disappear from what the client supplies, and clients read endpoints from the manifest instead of constructing hostnames themselves.
* **Stays endpoint metadata**: the manifest advertises regional URLs and a stable global authorization URL. Live capabilities and readiness remain the responsibility of the serving APIs. Adding this static URL does not add leader status, health aggregation, or a discovery runtime.

### Negative

* The CDN serving stack carries operational cost per environment: one-time managed-SSL certificate provisioning for the discovery hostname, and cache invalidation/refresh so a changed region list propagates promptly rather than waiting out the TTL.
* **Metadata-derived, not health-gated**: a region can appear in the manifest shortly before its endpoints converge, or should be dropped before teardown. Closing this gap is a second client lookup against the region platform-api-server's existing health API, not the manifest alone.
* The manifest is public: it exposes no secrets — only regional and global endpoint mappings for provisioned frontends. Discovery introduces no identifiers of its own; making the existing OIDC/platform-api hostnames opaque (to decouple them from `infra_id`) is a separate naming decision, out of scope here.

## Cross-Cutting Concerns

### Reliability:

* **Scalability**: One small JSON per environment, edge-cached; new regions are added entries with no architectural change.
* **Observability**: Cloud CDN / load-balancer request and cache-hit metrics in Cloud Monitoring; generation is auditable via PR + TFC run logs.
* **Resiliency**: Serve-while-stale keeps discovery working through origin disruption, and discovery and the platform API have no runtime dependency on each other.

### Security:

* Endpoint data is non-secret and served public read-only (open design); the GCS origin stays **private**, reached via Internet NEG + HMAC.
* **Discovery advertises; the server enforces.** The manifest is never an authorization boundary — the platform API is the authoritative validator at cluster-create, so a stale client is never the gate.
* Least privilege: the serving stack lives entirely in the per-environment service project; the discovery-serving stack's only cross-project grant is a single DNS write from that project into the global-owned apex zone (`{env}.gcp-hcp.devshift.net`), for the one `discovery` record — one grant per environment. Global authorization routing has its own narrowly scoped infrastructure permissions; the discovery publisher does not acquire regional leadership or routing authority.

### Cost:

* ~$18/month per environment for the discovery-serving stack (dominated by the global forwarding rule), consistent with GCP-621; no compute cost and negligible egress for a small JSON. This estimate excludes provisioning and operating authorization endpoint routing.

### Operability:

* Opt-in per environment; environments not using discovery are untouched.
* Deployed through the existing Terraform / HCP Terraform GitOps flow — no manual steps and no operator access surface.
* Debugging needs only the committed metadata and the published object — no cluster access, no PAM.

## Contract

* **Input**: environment + public GCP region. The environment maps to one fixed, public discovery URL known to the client.
* **Output**: a versioned JSON document returning regional OIDC/platform API endpoints and the stable global authorization endpoint. Regional entries remain keyed by public GCP region. Discovery publishes hostnames provisioned by infrastructure; it does not invent them. A client's explicit endpoint overrides continue to take precedence over discovery.

### Global Authorization Endpoint

Extend the manifest using a versioned schema with separate `regions` and `global` sections. Serve schema version 2 at a distinct versioned path (for example `/v2/endpoints.json`) alongside any existing region-only artifact. Keep the legacy artifact and its regional field names unchanged so older clients cannot mistake `global` for a region. Roll out the new client/schema support before depending on global discovery; do not replace a legacy document in place with an incompatible shape.

Illustrative version 2 document (hostnames are examples, not deployed endpoint assertions):

```json
{
  "schemaVersion": 2,
  "regions": {
    "us-central1": {
      "oidc_issuer": "https://oidc.us-central1.integration.example",
      "platform_api_endpoint": "https://api.us-central1.integration.example"
    }
  },
  "global": {
    "authorization_endpoint": "https://authz.integration.gcp-hcp.devshift.net"
  }
}
```

Generate `global.authorization_endpoint` from committed per-environment infrastructure metadata and publish it only after its frontend is provisioned. Omit it for environments that have not enabled global authorization routing. Clients validate supported schema versions and HTTPS URLs; an absent field produces an actionable unsupported-configuration error unless an explicit endpoint override was supplied. Other resources continue to use regional discovery. The new client must not infer a leader from region order or silently fall back to a regional endpoint.

The global hostname routes through a Terraform-managed DNS target to the designated leader's existing regional public frontend. Infrastructure must provision the global TLS hostname, ingress route, and ESPv2 issuer/audience support on each promotion target. Advertise only the stable URL: keep current leader identity, readiness, and election out of the manifest. No new discovery service or cross-region request proxy is introduced.

During [manual replication failover](../../implementation-plans/gcp-cross-region-resource-replication.md#manual-failover), fence the old leader, complete the required transfer/recovery checks, and verify the target's leadership generation, Cedar readiness, TLS, and authentication before changing the DNS target through GitOps. The discovered URL and customer configuration remain unchanged. A health check must never select a healthy follower as a replacement leader.

Stale DNS and existing connections may still reach the old endpoint. A server reached through the global hostname must reject **all** authorization operations, including GET/LIST, unless it is the designated ready leader. Validate the hostname at ingress and pass only trusted routing identity to the API guard. Regional hostnames may still serve authorized follower reads. Keep the old endpoint fenced after cutover and recovery; TTL expiry alone is not a correctness mechanism. The client reports unavailable/read-only errors without silently replaying mutations. Discovery cache refresh is independent of routing cutover and does not elect or promote a region.
